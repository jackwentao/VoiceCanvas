# VoiceCanvas 接口与数据模型设计

> 本文档定义 VoiceCanvas MVP 阶段的数据模型、内部端口接口、AI 动作协议、命令协议、流式更新协议和后端接口。后续实现时应优先在 Python 后端创建 Pydantic 模型，并在前端同步 TypeScript 类型，保证 AI 输出、命令执行、画布渲染、历史记录和存储导出使用同一套数据结构。

## 设计目标

- 统一数据模型：Project、Scene、CanvasElement、Command、Patch、History 使用同一套类型。
- AI 可控执行：AI 只能输出动作、命令或工具调用，不能直接覆盖 Project。
- 支持流式更新：CommandExecutor 每执行成功一条或一批命令，产生 CanvasPatch 推动画布局部刷新。
- 支持可恢复会话：Orchestrator 可以暂停到 `WAITING_FOR_USER`，等待用户语音或点击回答后继续。
- 前后端可分离：前端负责交互和渲染投影，Python 后端负责可信状态、AI 编排、命令执行、LLM、ASR 和七牛云存储适配。
- 易测试：每个模型和接口都能用 Mock 实现做单元测试或集成测试。

## 命名约定

ID 使用带前缀的字符串，便于调试和日志阅读：

```ts
type ProjectId = `project_${string}`;
type SceneId = `scene_${string}`;
type ElementId = `el_${string}`;
type CommandId = `cmd_${string}`;
type SessionId = `session_${string}`;
type AssetId = `asset_${string}`;
type HistoryEntryId = `history_${string}`;
```

时间统一使用 ISO 字符串：

```ts
type ISODateTime = string;
```

坐标系统约定：

- 画布左上角为原点。
- `x`、`y` 表示元素左上角。
- `width`、`height` 必须大于 0。
- `rotation` 单位为度。
- `zIndex` 越大越靠前。

### 编排循环约束

一次用户输入不等于一次 AIAction。`AIOrchestrator.next()` 每次只产出“下一步动作”，应用层通过 `runOrchestratorLoop` 持续执行，直到 session 进入 `WAITING_FOR_USER`、`COMPLETED`、`FAILED` 或 `CANCELLED`。

循环规则：

- `PLAN_TASKS`：保存 `TaskPlan`，写入 `plan_updated` observation，然后继续调用 `AIOrchestrator.next()`。
- `CALL_TOOL`：执行工具，写入 `tool_result` observation，然后继续调用 `AIOrchestrator.next()`。
- `EXECUTE_COMMANDS`：批量执行命令，写入 `command_result` observation，然后继续调用 `AIOrchestrator.next()`。
- `ASK_CLARIFICATION`：保存 `PendingClarification`，session 进入 `WAITING_FOR_USER`，等待用户语音或点击回答。
- `RESPOND`：通常用于本轮总结或普通回复，由应用层判断是否将 session 标记为 `COMPLETED`。

因此，`EXECUTE_COMMANDS.commands` 可以是一批命令，但它不是“本轮结束”的信号。真正的结束由 session 状态决定。

## 应用层端口接口

这些接口是模块解耦的边界。实现可以是本地 Mock、浏览器 API、真实 LLM、七牛云或 FastAPI 后端。

```ts
interface AIOrchestrator {
  next(input: OrchestratorInput): Promise<AIAction>;
}

interface CommandValidator {
  validate(commands: CanvasCommand[], project: Project): ValidationResult<CanvasCommand[]>;
}

interface CommandExecutor {
  execute(command: CanvasCommand, project: Project): Promise<CommandExecutionResult>;
  executeBatch(commands: CanvasCommand[], project: Project): Promise<BatchExecutionResult>;
}

type CommandExecutionResult = {
  commandId: CommandId;
  project: Project;
  patches: CanvasPatch[];
  historyEntry: HistoryEntry;
```

## 校验规则

必须校验：

- Project 至少有一个 Scene。
- `activeSceneId` 必须指向现有 Scene。
- Scene `order` 在同一个 Project 内不能重复。
- Element 坐标和尺寸必须是有限数字，`width`、`height` 必须大于 0。
- Element `zIndex` 在同一 Scene 内允许重复，但渲染层需要稳定排序。
- Connector 的 `from.elementId` 和 `to.elementId` 如果存在，必须指向同一 Scene 内的元素。
- 删除当前激活 Scene 后，必须切换到另一个 Scene。
- 清空、删除多个元素、删除 Scene、覆盖导出等风险操作需要确认或澄清。
- AIAction 必须符合 Schema，未知字段可以保留在 metadata，但不能影响执行。
- UserMemoryItem 的 `confidence` 必须在 0 到 1 之间。
- `ai_inferred` 类型来源的长期记忆默认应进入 `pending_confirmation`，除非置信度达到产品设定阈值。
- 用户当前明确指令优先于长期记忆。

## 测试建议

每个模型和端口都需要测试：

- 数据模型测试：Project、Scene、CanvasElement 的最小合法样例和非法样例。
- 命令 Schema 测试：每类 Command 的合法/非法 payload。
- CommandExecutor 测试：每条命令执行后 Project、Patch、History 是否一致。
- CanvasPatch 测试：Patch 能驱动画布局部更新，且可追溯到 commandId。
- History 测试：撤销、重做、部分失败记录。
- Orchestrator 测试：Mock LLM 返回 `PLAN_TASKS`、`CALL_TOOL`、`EXECUTE_COMMANDS`、`ASK_CLARIFICATION`、`RESPOND` 后流程正确。
- 编排循环测试：工具结果和命令执行结果会写入 observation，并触发下一轮 `AIOrchestrator.next()`。
- Session 测试：`WAITING_FOR_USER` 保存、恢复、取消。
- EventBus 测试：阶段、进度、澄清、总结事件按顺序发出。
- ToolRunner 测试：只读工具无副作用，写入工具必须走 CommandExecutor。
- MemoryRepository 测试：偏好保存、检索、更新、归档、候选记忆接受/拒绝。
- MemoryRetriever 测试：能根据用户输入和项目上下文检索相关偏好。
- MemoryExtractor 测试：能从重复行为或明确表达中生成候选记忆，低置信度记忆不直接生效。
- HTTP/SSE 测试：验证 FastAPI 启动、恢复、取消、事件流和导出接口。

- FastAPI 后端与 SSE 事件流。
- 长期记忆的可视化管理入口，例如查看、删除或确认候选偏好。
