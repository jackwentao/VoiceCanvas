## 产品定位

VoiceCanvas 是一个面向内容创作者的纯语音创作草图工具。用户可以通过说话创建、修改、组织和导出单张场景草图或短视频分镜草稿。

项目重点不是生成一张不可编辑的精美图片，而是帮助用户把创意快速变成可沟通、可修改、可导出的视觉草稿。

## 目标用户

优先服务短视频内容创作者，包括但不限于：

- 带货视频创作者
- 探店视频创作者
- 知识教程类创作者
- 需要快速表达画面想法的策划、运营、编导或产品人员

## 核心商业价值

传统文生图工具擅长生成单张结果图，但不擅长持续、精确、低成本地修改画面。VoiceCanvas 的价值在于：

- 用语音降低创作门槛，用户不需要掌握 PS、Figma 或复杂 prompt。
- 用结构化画布保留可编辑性，支持移动、缩放、删除、改文字、改镜头。
- 用分镜组织能力服务短视频创作，而不是只生成单张图片。
- 用元素级生成或占位策略补足素材缺口，避免整图反复生成带来的不可控和高成本。

一句话差异化：

> VoiceCanvas 不是 Voice-to-Image，而是 Voice-to-Editable-Storyboard。

## 成功指标

### 用户价值指标

MVP 是否成功，首先看用户能否只靠语音完成一次完整创作闭环：

- 从一句创意创建出单张草图或多镜头分镜。
- 能继续用语音添加、修改、删除元素。
- 能通过箭头、连接线和画面说明表达元素关系。
- 能通过画面说明判断 AI 是否理解了自己的需求。
- 能在左侧画布历史区看到镜头历史、操作历史和关键变更记录。
- 能在右侧 AI 交互栏看到当前阶段、澄清问题、执行进度和本轮变更总结。
- 能撤销错误操作，并导出可沟通的结果。

核心体验目标：

> 用户在不使用鼠标和键盘进行核心创作操作的情况下，能在 3 分钟内完成一组可展示、可修改、可导出的创作草稿。

### 演示成功指标

Demo 至少应稳定展示以下能力：

- 语音创建一个三镜头带货分镜。
- 创建过程中画布逐步更新，用户能看到镜头和元素陆续出现。
- 每个镜头生成画面草图、字幕/旁白、镜头说明和画面说明。
- 语音添加元素，例如商品、人物、标签、文字、箭头或连接线。
- 语音修改指定元素，例如移动、缩放、改文字、改颜色。
- 语音管理镜头，例如新增、删除或切换镜头。
- 左侧画布历史区展示镜头历史、操作历史和关键变更记录。
- 右侧 AI 交互栏展示任务阶段、澄清选项、执行进度和本轮变更总结。
- 语音撤销一次错误操作。
- 导出图片和 JSON 项目数据。

### 解析与执行指标

为保证系统不是只能跑固定 Demo，MVP 需要满足以下可测试指标：

- 覆盖至少 9 类指令：创建、镜头管理、添加元素、修改元素、删除元素、布局/图层、风格、历史控制、导出。
- 每类指令至少准备 3 条测试语料。
- AI 编排输出的结构化动作或命令通过 Schema 校验后才能执行。
- 对指代不明确的指令，例如“把它放大一点”，进入可恢复澄清流程，用户用语音或点击回答后继续原任务。
- 未知元素不能直接失败，至少生成语义占位元素。

### 工程质量指标

为匹配比赛评审中的“开发过程与质量”，MVP 需要满足以下工程指标：

- AI 编排、可恢复会话、画布状态、命令执行、历史记录、导出模块保持解耦。
- 画布流式更新基于 CommandExecutor 产生的增量事件，不能绕过命令校验。
- 左侧画布历史区只订阅历史和增量事件，不直接修改画布状态。
- 右侧 AI 交互栏只订阅 Orchestration 运行事件，不直接修改画布状态。
- 用户长期记忆与当前项目状态分离存储，长期记忆只作为 AI 上下文建议，不直接修改画布。
- 每个核心模块都有可运行测试。
- 画布状态可以导出为 JSON，并能用于复现当前草图。
- 普通编辑操作不依赖生图模型，避免每次修改都产生高成本调用。
- 不确定或低置信度场景进入澄清流程，而不是静默失败或强行猜测。
- 低置信度长期偏好需要用户确认后再写入，用户可以查看、修改或删除长期记忆。

### 成本与性能指标

MVP 阶段的成本控制目标：

- 移动、缩放、改文字、改颜色、撤销、重做等普通操作不调用大模型或生图模型。
- 未知元素优先使用语义占位；如接入生图，只按元素级生成，不整图重生成。
- 自然语言理解统一由 AI Orchestrator 处理；普通编辑操作在 AI 输出结构化命令后由本地 CommandExecutor 确定性执行，不再调用生图模型。
- 常见语音指令从识别完成到画布更新，目标响应在 1 秒内；复杂生成类指令允许异步完成。

## 关键产品决策

### 决策 1：选择“AI 语音绘图工具”作为参赛题目

结论：选择题目二“AI 语音绘图工具”。

理由：

- 72 小时内更容易做出完整闭环。
- 语音指令解析、画布状态、撤销重做、导出等模块更容易测试。
- 更容易体现架构清晰度、可扩展性和工程质量。

### 决策 2：主场景聚焦内容创作者，但不限制用户自由创作

结论：产品重点优化短视频分镜草图，但基础能力必须支持自由语音绘图。

理由：

- 只做带货或固定模板会显得产品过窄。
- 题目本质要求是纯语音绘图工具，不能只做分镜模板生成器。
- 用户可能只是想画一个单张草图，例如“画一棵树”“画一个桌子后面有恐龙”。

影响：

- 系统需要同时支持自由画布模式和分镜模式。
- 分镜本质上可以理解为多个小画布的集合。

### 决策 3：采用“结构化画布 + 元素级生成/降级”的方案

结论：画布内容应由结构化元素组成，而不是一整张不可编辑图片。

每个元素至少包含：

```ts
{
  id: string;
  name: string;
  type: "shape" | "text" | "template" | "generated_asset";
  x: number;
  y: number;
  width: number;
  height: number;
  zIndex: number;
}
```

理由：

- 可以精确支持语音修改，例如“把恐龙放大”“删除优惠标签”“把标题移到右上角”。
- 可以支持撤销、重做和 JSON 导出。
- 可以降低成本，普通编辑不需要重新调用生成模型。

### 决策 4：未知元素不直接失败，采用占位或元素级生成

结论：用户说出系统未内置的对象时，MVP 不能报错中断创作。

处理策略：

- MVP 保底：生成语义占位元素。
- 增强实现：调用生图模型生成透明背景素材。
- 所有未知元素生成后仍进入统一画布图层系统。

示例：

- 用户说“画一只恐龙”。
- 系统可以生成“恐龙”占位元素，或生成一个独立恐龙素材。
- 后续仍可语音移动、缩放、删除该元素。

### 决策 5：不承诺任意对象的无限内部编辑

结论：复杂对象内部编辑采用分层模板、整体替换或局部再生成，而不是临时拆成一堆不协调素材。

理由：

- 动态分别生成“杯子、奶茶液体、珍珠、吸管”再拼接，容易出现透视、光照、比例和风格不一致。
- 对高频商业元素，可以提前准备协调的分层模板。
- 对低频复杂元素，作为整体素材处理更稳定。

处理策略：

- 高频元素：使用预制分层模板，例如珍珠奶茶、手机、耳机、商品卡片。
- 非模板元素：整体生成或语义占位。
- 内部修改：模板元素改子层；非模板元素通过重新生成、局部修图或替换降级处理。

### 决策 6：支持简单图层和遮挡关系，但不在 MVP 做复杂图形引擎

结论：MVP 支持基础空间关系，包括前后、左右、上下、居中、置顶、上一层、下一层。

理由：

- “恐龙在桌子后面”这类表达需要最基本的图层和遮挡能力。
- 完整 Scene Graph、遮罩、约束布局可以作为未来扩展。

MVP 实现方式：

- 使用 `zIndex` 控制前后。
- 使用坐标和尺寸控制布局。
- 必要时用简单矩形遮挡模拟前景遮挡后景。

### 决策 7：支持关系表达和画面说明

结论：MVP 应支持箭头、连接线和画面说明，让用户不仅能画出元素，还能表达元素之间的关系，并检查 AI 是否理解了自己的需求。

理由：

- 内容创作者的草图不只是视觉摆放，还需要表达“谁指向谁”“什么导致什么”“这个区域是什么意思”。
- 箭头和连接线是正常画图软件的基础能力，也是分镜、流程、构图说明中高频使用的表达方式。
- 每个画布或镜头旁边保留一段 AI 生成的画面说明，可以帮助用户快速判断系统是否理解了指令。

影响：

- 元素类型需要增加 `arrow` 和 `connector`。
- 每个画布或镜头需要保存 `description` 字段。
- 修改镜头说明和修改画面说明应作为 MVP 支持的语音指令。

### 决策 8：采用可恢复 AI 编排器架构

结论：所有用户语音或文本输入统一进入 AI Orchestrator，不再设计规则解析主路径，也不在 AI 之前判断命令复杂度。

AI Orchestrator 每一步可以输出以下动作：

- `PLAN_TASKS`：把复杂需求拆成任务列表，保存到当前编排会话。
- `EXECUTE_COMMANDS`：执行当前可确定的一组结构化画布命令。
- `CALL_TOOL`：调用只读或写入工具查询/推进任务。
- `ASK_CLARIFICATION`：向用户澄清不确定信息。
- `RESPOND`：普通回复，不修改画布状态。

这些动作运行在 `runOrchestratorLoop` 中。工具结果和命令执行结果会作为 observation 回灌给 Orchestrator，AI 可以继续输出下一批命令、继续调用工具、询问用户或总结完成；因此 `EXECUTE_COMMANDS` 执行完不代表本轮任务结束。

理由：

- 用户指令复杂度无法提前可靠分类，同一句话可能需要直接执行，也可能需要先查询上下文。
- AI 更适合根据当前画布、历史操作和对话上下文判断下一步动作。
- 统一入口能减少多套解析链路带来的分支复杂度。
- 循环执行模型能承接“先计划、再多批命令、再观察结果、再继续”的复杂任务。
- 所有写操作仍然经过 Command Validator 和 CommandExecutor，保证状态稳定、可撤销、可测试。

### 决策 9：澄清不是取消，而是暂停后恢复

结论：当 Orchestrator 无法确定用户意图时，系统进入 `WAITING_FOR_USER` 状态，保存当前任务会话、待澄清问题、候选项、工具观察结果和已执行命令。用户后续可以用语音或点击选项回答，系统恢复同一个会话继续执行。

示例：

```text
用户：把标题放上面
系统：当前有主标题和价格标题，你想移动哪一个？
用户：主标题
系统：恢复原任务，并把主标题移动到画布上方。
```

理由：

- 语音创作需要自然连续的交互体验，不能每次追问都中断任务。
- 用户回答经常是“第一个”“主标题”这类短语，必须结合上一轮 pending clarification 理解。
- 该机制接近计划模式的交互体验：系统边执行边确认，确认后继续完成任务。

### 决策 10：左侧画布历史区、右侧 AI 交互栏与画布流式更新

结论：页面左侧固定为画布历史区，右侧固定为 AI 交互栏，主画布支持流式更新。用户主要通过语音与系统沟通，右侧 AI 交互栏负责展示语音识别状态、当前任务阶段、澄清问题、执行进度和本轮变更总结；左侧画布历史区负责展示镜头历史、操作历史和关键变更记录。

右侧 AI 交互栏至少包含：

- 语音输入入口和实时转写。
- 当前阶段，例如“正在理解需求”“正在创建镜头”“等待你选择标题”“正在总结变更”。
- 澄清问题与可选项，支持语音回答和点击选择。
- 复杂任务的执行进度。
- 本轮变更总结，例如新增了哪些镜头、修改了哪些元素、删除了哪些内容、是否导出成功。

画布流式更新规则：

- AI 可以一次生成多条命令，也可以通过工具调用逐步推进任务。
- CommandExecutor 每执行成功一条或一批命令，就产生 CanvasPatch。
- Canvas Renderer 订阅 CanvasPatch 并局部刷新，用户可以看到内容逐步出现。
- 如果后续命令失败，已经成功执行的变更保留，并由右侧 AI 交互栏说明当前完成情况和下一步建议，左侧画布历史区记录已成功执行的操作。

理由：

- 复杂语音任务如果等待全部完成后再刷新，用户会感觉系统卡住或不可控。
- 右侧 AI 栏能让用户始终知道系统在听、在想、在执行、在等待回答，降低语音交互的不确定感。
- 左侧画布历史区能让用户回看画布如何一步步形成，便于撤销、复盘和继续迭代。
- 本轮总结可以帮助用户确认 AI 对需求的理解和实际变更，便于继续用语音迭代。
- 画布流式更新和 AI 交互栏都通过事件订阅实现，保持 UI、AI 编排和命令执行解耦。

### 决策 11：支持用户长期记忆作为加分项

结论：除当前项目短期记忆外，VoiceCanvas 增加 User Memory 模块，用于保存跨项目有效的用户偏好、命名习惯、布局习惯和风格偏好。短期记忆以画布状态、历史记录和当前编排会话为主；长期记忆以用户画像形式独立保存，并作为 AI Orchestrator 的上下文建议。

长期记忆示例：

- 用户习惯把第一个分镜叫做“主图”。
- 用户说“太阳”时，通常喜欢放在左上角。
- 用户偏好清爽绿色、小红书风或简洁促销风。
- 用户创建带货分镜时，常用“主图、卖点、转化”三段结构。

使用规则：

- 用户当前明确指令优先于长期记忆。
- 长期记忆不能直接绕过 CommandValidator 或 CommandExecutor。
- AI 从行为中推断出的低置信度偏好，应先进入候选记忆，由右侧 AI 交互栏询问用户确认。
- 用户必须能查看、删除或修改长期记忆，避免错误偏好长期污染体验。

理由：

- 这是比赛中的差异化亮点：系统不是只会完成一次绘图，而是越用越懂用户。
- 对纯语音创作尤其有价值，可以减少重复表达，例如默认命名、默认布局、默认风格。
- 长期记忆独立于 Project State，既能跨项目复用，又不会破坏当前项目的可导出、可复现能力。

## MVP 功能清单

### 1. 创建项目/分镜

MVP：

- 创建自由画布
- 创建分镜
- 根据主题生成初始内容
- 创建过程中画布逐步更新

### 2. 画布/镜头管理

MVP：

- 新增镜头/画布
- 删除镜头
- 切换镜头

加分项：

- 复制镜头
- 排序镜头

### 3. 添加元素

MVP：

- 添加人物
- 添加商品
- 添加文字
- 添加标签
- 添加箭头
- 添加连接线
- 添加背景
- 添加未知元素

说明：未知元素在 MVP 中至少以语义占位形式出现；如果进度允许，再接入元素级生成。

### 4. 修改元素

MVP：

- 改文字
- 改箭头/连接线文字
- 改颜色
- 改大小
- 改位置
- 改时长
- 改镜头说明
- 改画面说明

### 5. 删除元素

MVP：

- 删除元素
- 删除镜头

加分项：

- 删除模板子层，例如“删掉珍珠”

### 6. 调整布局/图层

MVP：

- 放到左边
- 放到右下角
- 居中
- 上一层
- 下一层
- 置顶

加分项：

- 放到桌子后面
- 前后遮挡关系
- 更复杂的空间关系

### 7. 风格调整

MVP：

- 清爽
- 科技

### 决策 12：短期指代记忆从真实 Patch 后提取，过期对话直接淘汰

结论：为解决“画一个狗”后用户继续说“往左移一点”这类省略指代问题，系统新增项目内短期记忆，但不引入复杂压缩链路。短期记忆在 CanvasPatch 已发送给前端之后，从真实执行结果中提取最近操作主体；过期对话轮次直接按窗口淘汰，只保留少量最近主体作为保底 focus。

短期记忆包含：

- `focusStack`：最近被创建、修改、选中或恢复的画布元素主体，用于解析“它、这个、刚才那个、往左移一点”等近期指代。
- `recentTurns`：最近若干轮用户输入和系统摘要，用于补充 LLM 对上下文的理解。

处理规则：

- Patch 先发给前端，再提取短期记忆，保证用户先看到画布变化。
- 短期记忆提取只使用本地规则和真实 Patch，不调用 LLM，不增加用户感知延时。
- 超出窗口的对话轮次直接丢弃，不做复杂压缩；明确对象仍可从当前 Project 中查找。
- 长期记忆只作为后续异步候选能力，不参与普通“它/这个”类近期指代的默认解析。
- 如果用户明确说“以后都这样”“记住这个偏好”，才考虑沉淀长期记忆，并应低置信度确认。

理由：

- 自然对话中的省略指代主要依赖近期语境，直接压缩长期对话会增加实现复杂度和误匹配风险。
- 真实 Patch 比 Planner 草稿更可靠，因为它包含系统最终补齐的 elementId、执行后的坐标和真实变更结果。
- 短期规则记忆能在毫秒级完成，符合语音创作对即时反馈的体验要求。

### 决策 13：所有功能必须通过小粒度 PR 交付并声明依赖边界

结论：本项目所有后续功能都必须基于 Pull Request 交付。每个 PR 只实现或修改单一功能，鼓励尽可能小、粒度尽可能细；大功能必须拆成多个可独立验证、可独立合并的 PR 分步提交。

PR 内容要求：

- 标题：一句话说明本 PR 新增或修改了什么。
- 功能描述：说明功能作用与使用方式。
- 实现思路：说明技术选型、架构边界或核心实现逻辑。
- 测试方式：列出评委或开发者可以复现的验证命令与场景。

依赖与原创性要求：

- 涉及第三方库或框架时，必须在 README 或技术选型文档中列明依赖名称、用途和引入边界。
- 必须说明本项目原创功能部分，避免把第三方能力误写成自研能力。
- 如果本次 PR 未新增第三方依赖，也应在相关文档中明确说明“未新增第三方依赖”。

合并要求：

- PR 合并后主分支必须保持可运行状态，评委在任意时间查看主分支都应能复现演示效果。
- 每个 PR 必须补充或更新对应测试，测试通过后再提交合并。
- 涉及作品有效性、依赖合规或原创边界的改动，必须同步更新文档。

### 决策 14：素材包优先覆盖高频带货品类，并通过 MinIO 后端代理渲染

结论：MVP 不为每个用户描述实时生成或手绘大量图片，而是先准备一套统一风格的高频带货素材包。每个常见品类先准备 1 个主体素材，素材统一存放在 MinIO；Render Catalog 只保存稳定对象路径、别名和可结构化保存的属性，前端通过后端代理 URL 渲染。

首批素材优先覆盖：

- 食品饮料：奶茶。
- 美妆护肤：护肤瓶。
- 数码 3C：手机。
- 服饰鞋包：运动鞋。
- 家居日用：收纳盒。
- 母婴个护：奶瓶。
- 宠物用品：宠物粮袋。
- 零食生鲜：零食包装。

处理规则：

- 先匹配主体，再处理属性。用户说“草莓味珍珠奶茶”时，主体匹配 `bubble-tea`，草莓味、珍珠作为属性和卖点保存，不因为缺少专门的草莓奶茶图而占位。
- LLM 不输出图片 URL，只输出 `renderKey`、语义主体和属性；MinIO 对象路径由 `render-catalog.json` 管理。
- 前端不直连 MinIO，不暴露桶信息或凭证；只请求后端 `/api/assets/catalog` 获取代理 URL。
- 通用标签、价格、优惠、低糖、新品、箭头、连接线、背景块继续使用结构化元素生成，不为每个品类重复准备。
- MinIO 不可用或素材缺失时，元素仍保留为 `generated_asset` 占位，创作流程不中断。

理由：

- 统一素材风格比临时拼接多来源图片更适合比赛 Demo，也更稳定。
- 每类先准备一个主体素材，能快速覆盖带货高频场景，避免素材工作量膨胀。
- 属性结构化保存后，后续仍可以通过文字标签、颜色、卖点说明和局部样式表达差异。
- 后端代理 MinIO 符合当前解耦架构，后续可替换为七牛云或其他对象存储。

影响：

- `render-catalog.json` 成为素材语义目录和对象路径事实源。
- 后端新增素材路径校验与代理读取接口。
- `generated_asset.metadata` 可包含 `assetProvider`、`assetPath`、`styleFamily`。

## 明确不做

MVP 不做以下内容：

- 不做真正视频生成
- 不做完整视频剪辑器
- 不做 PS/Figma 级精细编辑
- 不承诺任意复杂物体的内部拆解
- 不承诺所有自然语言都能完美理解
- 不把整张图生图作为核心方案
- 不做复杂骨骼动画或完整时间轴

## 主演示流程

优先演示带货短视频分镜，但产品能力不限制在带货模板。

建议演示链路：

1. 用户说：“创建一个三镜头的珍珠奶茶带货分镜，主打低糖和新品上市。”
2. 系统生成三个镜头：痛点/钩子、产品特写、优惠转化。
3. 系统在每个镜头旁边生成画面说明，复述 AI 对画面和意图的理解。
4. 用户说：“把第二镜头里的珍珠删掉，改成低糖奶茶。”
5. 系统隐藏珍珠层，或替换为无珍珠奶茶模板。
6. 用户说：“给第二镜头加一个箭头，指向低糖标签，写上核心卖点。”
7. 用户说：“第三镜头加一个限时优惠标签，放到右下角。”
8. 用户说：“整体改成清爽绿色风格。”
9. 用户说：“撤销上一步。”
10. 用户说：“导出分镜。”
